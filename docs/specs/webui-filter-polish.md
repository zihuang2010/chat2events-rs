# webUI 优化：明细排序 · 商家分组 / 业务经理 · 筛选区重排 · 关键词语义 · 数据追溯消息总量

## Problem Statement

客服主管和运营在只读工作台上做日常核对时，碰到五个问题：

1. **数据追溯 / 事件明细**默认按归属日**正序**排，最新的事件沉在最后一页。每次进来都得先点一下「开始时间」表头，而且点到第三下排序会被取消，又回到正序。
2. **群聊洞察 / 群维度指标**里只看得到商家名，看不到群背后商家的**商家分组**和**业务经理**。这两个维度明明可以当筛选条件，表里却没有对应的列，筛完也没法确认筛对了。群详情抽屉里同样没有。
3. **筛选区排版不清楚**：第一行没有可见的字段名，只剩占位符；「更多筛选」夹在关键词和日期之间，像是关键词的附属按钮；商家分组、业务经理这两个「圈哪些群」的条件藏在「更多筛选」里，和群聊、客服不在一起。
4. **关键词到底搜什么，说不清**：悬停提示写的是「事件摘要、分类、群聊或客服」，实际上只匹配事件摘要。群聊洞察页还多一条只有它才有的规则：群名命中也会保留这个群，于是搜群名会出现事件量为 0 的行。四个页面上同一个输入框的意思不一样。
5. **数据追溯页没有消息总量**。事件量偏小时，没法在同一页判断是群里真的清静，还是抽取漏了。

## Solution

1. 事件明细默认按**开始时间倒序**，开始时间相同再按事件 ID 倒序。表头默认就显示倒序箭头，点「开始时间」只在倒序和正序之间切换。抽屉里的上一条 / 下一条跟着这个顺序走。
2. 群维度指标在「群」列右边新增「商家分组」「业务经理」两列，可以排序；群详情抽屉的标题下面加一行，显示同样的两项。显示规则：「未分组」照原样显示；业务经理查不到姓名时显示编号；其余缺失一律显示 `—`；排序时缺失值不管正序倒序都排在最后。
3. 筛选区重排成两行，所有字段名可见：
   - 第一行（范围）：日期范围 · 快捷时间 · 群聊 · 客服 · 商家分组 · 业务经理
   - 第二行：关键词，「更多筛选」和「重置」放在行尾
   - 「更多筛选」里只留**事件属性**：一级分类 · 二级分类 · 状态 · 超时条件
4. 关键词的字段名改成「事件摘要」，占位符写成例子，删掉不准确的提示。所有页面上的关键词都只有一个意思：**只看摘要里包含这个词的事件**。要找群用「群聊」下拉框，要找客服用「客服」下拉框，要找分类用分类下拉框。
5. 数据追溯页在「活跃群」后面加一张**消息总量**卡片，口径与事件洞察页的那张完全一致。

## User Stories

### 事件明细排序
1. 作为客服主管，我希望打开数据追溯页时最新的事件排在最前面，这样不用翻页就能看到昨天发生了什么。
2. 作为客服主管，我希望「开始时间」表头默认显示倒序箭头，这样我一眼就知道当前是怎么排的。
3. 作为客服主管，我希望点一下「开始时间」就切到正序、再点一下回到倒序，这样不会点出一个「看起来没排序」的状态。
4. 作为客服主管，我希望开始时间相同的事件之间顺序固定，这样翻页时同一条事件不会在两页里重复出现或者一页都不在。
5. 作为客服主管，我希望从其他页面（比如事件洞察的「无响应事件」卡片）跳到数据追溯时，同样默认是倒序，这样每次进来看到的都是同一种顺序。
6. 作为客服主管，我希望在明细抽屉里点上一条 / 下一条时，顺序与表格一致，跨页时也一样，这样连续核对不会跳着走。
7. 作为客服主管，我希望点首响时间、首响耗时、群等其他可排序列时行为不变，取消这些列的排序后回到默认的开始时间倒序。
8. 作为分享链接的人，我希望别人打开我发的、不带排序参数的数据追溯链接时，看到的顺序和我看到的一致。

### 商家分组与业务经理
9. 作为客服主管，我希望群维度指标表里每个群都显示它的商家分组，这样我能按分组比较群的表现。
10. 作为客服主管，我希望群维度指标表里每个群都显示它的业务经理，这样我知道该找谁跟进这个商家。
11. 作为客服主管，我希望商家分组为「未分组」的群照原样显示「未分组」，这样它与「更多筛选 → 商家分组」里的「未分组」选项对得上。
12. 作为客服主管，我希望业务经理只有编号、查不到姓名时显示编号，这样它与业务经理下拉框里看到的那一项对得上。
13. 作为客服主管，我希望没关联商家、查不到商家、商家没配经理的群显示 `—`，这样我能一眼分清「有值」和「没有」。
14. 作为客服主管，我希望能按商家分组、业务经理排序，缺失的群永远排在最后，这样排完以后有值的群挨在一起。
15. 作为客服主管，我希望商家名仍然挂在群名下面，这样新增两列后我不会丢掉已有的信息。
16. 作为客服主管，我希望打开群详情抽屉时也能看到这个群的商家分组和业务经理，显示规则和表格一样，这样不用关掉抽屉回表格去找。
17. 作为业务经理，我希望在筛选里选了自己之后，表格的「业务经理」列全是我的名字，这样我能确认筛对了。

### 筛选区排版
18. 作为工作台用户，我希望每个筛选控件上方都显示字段名，这样不用把鼠标悬停上去也知道它是干什么的。
19. 作为工作台用户，我希望日期、群聊、客服、商家分组、业务经理这些「圈范围」的条件在同一行，这样我先定范围再看细节。
20. 作为工作台用户，我希望商家分组和业务经理不用展开「更多筛选」就能用，因为我常用它们。
21. 作为工作台用户，我希望「更多筛选」和「重置」在行尾并排，这样它们看起来是整个筛选区的操作，而不是某个输入框的附属。
22. 作为工作台用户，我希望「更多筛选」里只有一级分类、二级分类、状态、超时条件这四项事件属性，这样我知道展开后能找到什么。
23. 作为工作台用户，我希望「更多筛选」按钮上的计数和收起时显示的条件标签只算这四项，这样数字和展开后看到的一致。
24. 作为工作台用户，我希望「更多筛选」收起时，里面生效的条件仍以可点掉的标签显示，这样看不见的条件不会悄悄改掉读数。
25. 作为工作台用户，我希望「重置」仍然清掉所有条件，包括第一行的商家分组和业务经理。
26. 作为工作台用户，我希望首响阈值仍然留在页头的「指标口径」里，因为它是口径而不是筛选条件。
27. 作为工作台用户，我希望窄屏下筛选控件能自动换行而不是被挤出屏幕。

### 关键词语义
28. 作为工作台用户，我希望关键词输入框的字段名写着「事件摘要」，这样我知道它只搜摘要。
29. 作为工作台用户，我希望占位符给出例子（比如退款、改地址），这样我知道该输入什么样的词。
30. 作为工作台用户，我希望不再看到「可以搜分类、群聊或客服」这种实际不成立的提示。
31. 作为工作台用户，我希望在群聊洞察、事件洞察、客服效能、数据追溯四个页面上，关键词都是同一个意思，这样换页面后不用重新理解。
32. 作为客服主管，我希望在群聊洞察输入关键词后，表里只剩下有命中事件的群，而不是混进一些群名碰巧命中、事件量为 0 的群。
33. 作为客服主管，我希望想找某个群时用「群聊」下拉框搜群名，这样结果是精确的一个群。
34. 作为客服主管，我希望关键词里的 `%`、`_` 照字面匹配，像现在一样。

### 数据追溯消息总量
35. 作为客服主管，我希望在数据追溯页看到所选日期与群范围内的消息总量，这样事件量偏小时能判断是群里清静还是抽取漏了。
36. 作为客服主管，我希望消息总量卡片紧跟在「活跃群」后面，和事件洞察页的位置一样，这样两页对照着看不会找错。
37. 作为客服主管，我希望卡片上注明「仅按日期、群统计」，这样我改了分类、客服、状态或关键词以后，看到它不变也不会以为是错误。
38. 作为客服主管，我希望有群日缺记录时卡片注明「仅已知量」、完全没有群日记录时显示「—」，这样不会把「没数据」当成「零条消息」。
39. 作为客服主管，我希望即使所有群日都抽取失败，消息总量仍然显示，因为消息数不依赖抽取。
40. 作为客服主管，我希望数据追溯页和事件洞察页在同一组条件下显示同一个消息总量。

### 注释与可维护性
41. 作为维护者，我希望后端与前端 API 客户端里「前端会把名字翻译成 ID 参数」的注释改成实话，这样后来的人不会照着一个不存在的机制去改。
42. 作为维护者，我希望客服效能页里「按摘要、群与客服统一下推筛选」的注释改成实话（关键词只按摘要下推）。
43. 作为维护者，我希望后端默认排序那里「与索引前缀同序，连 filesort 都不用」的说明更新为新的默认顺序及其代价。

## Implementation Decisions

- **事件明细默认顺序在后端定**：`/api/events` 不带排序参数时，按开始时间（首条来源消息时间）倒序，再按事件 ID 倒序。白名单里显式指定的排序（开始时间 / 首响时间 / 首响耗时 / 群 / 末条时间）行为不变：空值排最后，最后按事件 ID 正序兜底。默认顺序不再与覆盖索引前缀同序，会多一次窗口内排序；手动点「开始时间」排序时本来就是这个代价，默认 7 天窗口约 1.3 万行，可以接受。
- **前端只负责把默认顺序表现出来**：没有显式排序时，「开始时间」表头显示倒序箭头；这一列的点击顺序是倒序 → 正序 → 回到默认（即倒序），所以不会出现「无排序」状态。其他列取消排序后回到默认。URL 上不写默认排序。
- **模拟后端的默认顺序与真实后端保持一致**，否则前端测试测的是假顺序。
- **商家分组 / 业务经理的数据来源**：用页面加载时已经拿到的群元数据（筛选选项接口里每个群自带的分组名、经理编号、经理姓名），**不改 API、不改表结构**。
- **显示规则只写一处**：沿用「群背后的商家」那个取值函数的形状，在分析上下文里提供「这个群的商家分组」「这个群的业务经理」两个取值，表格和群详情抽屉共用；规则与业务经理下拉框的选项标签一致（有姓名用姓名，否则用编号）。缺失统一用现有的空值样式 `—`，不区分缺失原因。
- **排序**：两列都按中文排序规则比较；缺失值不管正序倒序都排在最后。
- **群详情抽屉**：在抽屉标题下面加一行信息，显示商家分组和业务经理，规则同上。抽屉仍然是固定 7 天、只看这一个群，与页面筛选无关。
- **筛选区**：共用的筛选组件改成两行（见 Solution）。商家分组、业务经理从「更多筛选」挪到第一行；「更多筛选」的计数与收起时的条件标签只统计四项事件属性。字段名全部可见（取消对第一行标签的视觉隐藏）。首响阈值的位置不动。
- **关键词**：后端语义不变，仍然只匹配事件摘要（包含匹配、元字符转义、首尾空白裁掉）。前端只改字段名、占位符，删掉不准确的提示。群聊洞察的群表**去掉群名 / 群 ID 命中规则**：有关键词时只保留至少有一个命中事件的群。
- **数据追溯的消息总量**：复用事件洞察页那张卡的取数与文案（所选日期与群范围内群日消息数之和、`METRIC.msgCount` 口径说明、「仅按日期、群统计」及「仅已知量 / 无群日记录」后缀），放在第 2 张。这张卡**不受**事件覆盖为零时的「不可用」状态影响。
- **术语**：「消息总量」已写进 `CONTEXT.md` 术语表，明确它不是「事件涉及的来源消息数」。
- **不涉及**：表结构、指标口径、金标向量、跑批。

## Testing Decisions

- **好测试的标准**：只断言外部行为。前端断言用户看得见的东西（表头、单元格文字、卡片标签与备注、筛选控件的字段名与位置、行顺序、抽屉内容），不断言内部函数的返回值、CSS 类名的组合或组件内部状态。后端断言接口契约（默认顺序这一条规则）。
- **接缝 A：页面级渲染测试（前端，主接缝）**。用模拟后端渲染整页。覆盖：
  - 数据追溯：不带排序参数时行按开始时间倒序；表头显示倒序箭头；点击开始时间切到正序、再点回到倒序；消息总量卡片位于第 2 张，数值和备注与事件洞察页一致。
  - 群聊洞察：两个新列存在；「未分组」原样显示、只有编号时显示编号、缺失显示 `—`；排序时缺失值始终在最后；群详情抽屉显示同样的两项；输入只命中群名的关键词时该群不再出现。
  - 筛选区：字段名可见；商家分组、业务经理在第一行；「更多筛选」只有四项，计数和收起标签只算这四项；关键词的字段名和占位符。
  - 已有参照：群聊洞察页、筛选组件、各洞察页的现有页面测试。
- **接缝 B：后端默认排序的单元测试**。现有的排序白名单测试里「默认」那条断言改成新的默认顺序；空排序参数仍按「没给」处理。
- **不新增接缝**：直接测试群表群名命中规则的单元用例随规则一起删除，由接缝 A 覆盖新行为；模拟后端的默认顺序由接缝 A 的行顺序断言兜住，不单独测；注释修正不需要测试。
- **不在本次运行**：需要 MySQL 的 `mysql_` 真实 SQL 测试。

## Out of Scope

- `agentRollup` 里关键词非空的那条死分支（只在整体概览调用、而整体概览的关键词恒为空）——不改，只记录。
- 让关键词同时匹配分类名、群名、客服名（需要改后端语义，且与三个可搜索下拉框重复）。
- 「事件来源消息数」这个新量（汇总事件的来源消息条数）。
- 整体概览页加筛选区；首响阈值挪位置。
- 群详情抽屉显示商家名称（没有要求）。
- 区分「没关联商家」「查不到商家」「没配经理」等缺失原因。
- 表结构、API 契约（除事件明细默认顺序外）、指标口径、金标向量的任何改动。

## Further Notes

- 在新分支上实现，不直接改 `main`；不 commit，除非另行要求。
- 验证：`cargo fmt --check`、`cargo test`、webui 的类型检查、lint 与测试，结果照实贴出。
- 显式 URL `sort=time&dir=desc` 仍然可用，它走白名单路径，最后按事件 ID **正序**兜底；不带参数的默认顺序按事件 ID **倒序**兜底。两者只在开始时间完全相同的行之间有差别，这是有意保留的，不必统一。
