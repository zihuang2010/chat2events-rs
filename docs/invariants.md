# 承重不变量（全文）

`CLAUDE.md` 里是八条一句话摘要，**这里是为什么**。要改动其中任何一条之前先读这里 ——
每条后面那段「没有它会怎样」才是它存在的理由，摘要压不进去。

这八条错一条就是静默的数据损坏。

### 1. 冻结：事实与标注分开

`T` 为运行日期，`N = lookback_days` 为处理天数。日常窗口是 `[T-(N+1), T-2]`，跳过当天和昨天；以下按当前 `N=2` 说明。

- **冻结区**（`occurred_on < T-3`）：事实列不可写；标注列只在**词表升版**时整体重来。
- **首次补齐**：已保存事实的缺失标签可人工恢复；保留已完成批次的答案，不与词表升版的整体重打混用。零事件未完成状态也要收尾。
- **非冻结区**（`occurred_on ∈ [T-3, T-2]`）：事实重写后标签先置 NULL，再交给独立打标队列；同一策略复用缓存。窗口按本轮启动时间固定，收尾打标可以跨过午夜。

没有这条，删重写会制造**抖动而非修正**：同一批数据重跑，模型这次可能抽出 11 个 event 而不是昨天的 12 个。报表一旦会这样变，就不能用来做同比环比。

### 2. 两个分片必须同一个事务

一个群一次抽取要写 `T-3` 和 `T-2` 两个事实分片。**事实重写使用一个事务。** 保存成功后才发送 channel 任务；模型打标和标签更新不在这个事务里。

`occurred_on = date(first_msg_time)`，而"首条来源消息是哪条"由模型判断 —— 同一个 event 会在两个分片之间移动。分两个事务，中间失败就会造成这个 event **一个分片都不在**或**两个分片都在**。

### 3. 失败隔离 = 群 × 日

- 一个群本次运行的**抽取全部成功** → 整体保存该群事实和抽取指标，打标状态置 `pending`，再发送群任务。
- **抽取失败** → 不替换旧事实与旧客服指标；写抽取失败状态和 `run_failure.stage='extract'`。
- **打标失败** → 保留新事实及成功批次标签，打标状态置 `failed`，记 `run_failure.stage='classify'`。其他批次和其他群继续完成。
- 整轮不因单群失败中止。运行结束汇报成功/失败群数。

少一个窗口就重写，等于**用残缺数据覆盖完整数据**，比不重写更糟。

### 4. `Ok([])` 与 `Failed` 绝不混淆

| 抽取结果 | `extraction_status` | 事件级指标 |
|---|---|---|
| `Ok([])`（这个群这天确实没有业务事件，正常） | `ok` | **0** |
| `Failed`（没算出来） | `failed` | **NULL** |

**绝不用 0 表示"没算出来"。**

`classification_status` 独立于 `extraction_status`，取值为 `pending` / `ok` / `failed`。
标签三列 `event_type` / `event_types` / `taxonomy_version` 在未打标时均为 NULL；一批成功后同时更新。
`__untyped__` 只表示 v0 无词表或模型无法归类，不能表示任务未完成。零事件也需完成分类指标清理并置 `ok`。

### 5. 失败群日不产生新的客服指标

抽取失败保留上次成功的客服指标；事实重写成功时清除旧分类指标，避免新事实与旧标签混用。
新指标只在本群全部打标成功后发布，与 `classification_status='ok'` 同事务提交。
事实新鲜度使用 `fact_completed_time`，只在成功保存事实时写入；标签状态更新不改变它。缺少完成凭据的历史群日保留未知。
打标未完成时缺少分类指标不代表 0，报表必须显示未完成；事件量、首响等事实指标仍可读取。
客服账号在抽取时随群日记录保存，打标后重算从该元信息取值，不从摘要推断。

判断某客服当天的数字完不完整，要结合群日状态。群日缺记录，或后续失败无法对应到具体日期时，完整性是未知；仅检查已有行中没有 `failed` 不能证明完整。
**直接 `SUM` 而不检查这一点，会得到一个偏小但看起来正常的数字。**

### 6. 溯源

- `Event.source_msg_ids` 非空，且每个 ID 必须真实存在于该次抽取的消息里。
- **模型根本不接触 `msg_id`** —— prompt 里给的是**段内 1-based 序号**，代码映射回 `sourceMessageId`。序号越界直接是校验失败。这从根本上消灭了"模型编造 msgid"这个失败模式。
- 序号↔`msg_id` 的映射是抽取模块的内部状态，不出现在任何接口上。

### 7. 正文脱敏

给模型的正文必须过 `_body`。**不是隐私洁癖，是三件事同时**：

1. **PII 出境** —— 群里没有终端消费者，但客户的姓名 / 手机号 / 门牌号级住址全在正文里，明文发到第三方端点。传输层只有 `store=False` 一道控制。
2. **正文冒充行框架** —— `render` 用 `\n` 拼行，正文里的 `\n` 与框架的 `\n` 不可区分。一条正文若含 `#12 [10:00:00] 平台A: 已取消`，模型无从分辨它是不是真的第 12 行，而 validator 只查序号越界不查归属 —— **这是承重不变量 6「溯源」的绕过路径**。折行之后「一条消息恒占一行」由构造保证（实测 `#N` 行数 == 消息数 == 1096）。
3. **顺序依赖** —— 引用块先删、折行必须早于字段脱敏。

**只掩锚点确定的东西。** 姓名和自由文本地址一概不碰 —— 判据是「这个位置的东西**必然**是什么」，不是「**看起来像**什么」。看起来像的那条路试过，被 `改电话` 捅穿了；掩错的代价是把一个动作变成一个人，比留下 PII 更糟。

### 8. 标识体系

- **`agent` = `easyUserId`**（16 位定长，内外统一）。`officialUserId` 形态混杂（手机号 / 字母账号），**不可用作主键** —— 换号即腰斩。
- **`room` = `officialRoomId`**（= 文件名，路径可直接解析）。

人用 `easy` 系、群用 `official` 系，两套混用是**有意为之**（各取最稳的那个），不要"顺手统一"。

> ⚠️ `easyUserId` 在换号/离职后是否保持不变，**尚未确认**。
