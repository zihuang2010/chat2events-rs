① 摄取 · pull.rs · ADR-0005

每天只把
新长出来的那一段抄回来

OSS 上一个群一个月只有一个文件，每天往它尾巴上接一截。
所以拉取不是「同步文件」，是量一下上游长到第几个字节，只搬中间那一段。

00

what upstream looks like先看上游长什么样：一卷会变长的纸带

不是「一天一个文件」。是 一个群 × 一个月 = 一个 NDJSON 文件，OSS 用 AppendObject 每天往尾部追加。月初 0.6 MB，月末 18 MB —— 同一个文件。

01

list_month_files() · MySQL第一步：问数据库要「尺子」

文件不靠 glob 目录发现，靠查 MySQL 索引表 b_wecom_group_message_month_file。 这张表一行 = 一个群一个月的文件，它同时回答了三件事：在哪、长到第几字节、共几行。

字段它说的事
ndjson_object_key相对 object key，拼上域名就是下载地址
ndjson_position下一批追加的预期字节位置 = 权威文件末尾
ndjson_record_count已确认追加的记录数 = 一道免费的、独立于字节数的校验
file_month消息月份 yyyyMM（不是接收月份）
corp_id / official_room_id哪个企业、哪个群
is_deleted0 正常 / 1 冻结，筛选条件

查哪几个月？由跑批窗口 [T-2, T-1] 决定 —— months(w) 把窗口里的每天格式化成 %Y%m 再去重。月初那几天窗口跨月，同一个群就有两行。

// src/pull.rs · 上游字段名只允许出现在这里
SELECT corp_id, official_room_id, file_month, ndjson_object_key,
       ndjson_position, ndjson_record_count
FROM   b_wecom_group_message_month_file
WHERE  is_deleted = 0 AND file_month IN (?, ?)   ← ["202608","202609"]
ORDER BY corp_id, official_room_id, file_month

只有占位符个数是拼出来的（months.len() 决定），月份的值一律走 bind， 没有任何外部数据参与拼串。这张表查不动 = 整轮失败（PullError::Round）， 那不是某个群的事。

02

have = fs::metadata(local).len()第二步：量一下本地已经有多长

本地是 OSS 的字节级镜像 —— 同一个群同一个月，本地这个文件的内容和 OSS 上前 N 字节 逐位相同。于是「我已经拉到第几字节」这个状态不需要任何数据库、任何 manifest：

have = 文件大小        // 文件不存在就是 0
<raw_root>/<yyyyMM>/<corpId>/<roomId>.ndjson
   ./data/raw / 202608 / ww05b0ccc262c50187 / wr1pO5VgAAfuGk8URr_9uTqNDVsCfgow.ndjson

路径不是在 pull.rs 里拼的 —— 它管 ingest::room_path() 要， 跟读文件用的是同一个函数。写和读永远不会对不上。

03

pull_one() · 四选一比一下两个数字，四种结果

position == 0
Empty
上游登记了但还没数据，什么都不做。
have == position
Skip
已经是最新，零字节下载。天然幂等。
have > position
作废重拉
本地比上游还长（上游删档重建）。删掉本地、have = 0，打一条 WARN。
have < position
下载中间那一段
只要 position - have 这么多字节。

为什么必须处理第三种？追加写本来不该出现这种事 —— 但不处理的话这个群会每天校验失败、永远跑不了。

04

HTTP Range · 206 Partial Content第三步：只把新的那一段搬回来

有些 CDN 会无视 Range 直接返 200 整个对象。那就自己切： body.slice(have..)。要是整个对象反而比本地已有的还短 —— 直接判这个群失败。

05

write_and_verify()落盘之前，三道检查

任何一道没过，一个字节都不写。不修补、不截断、不落一半。

  • 01
    字节数必须分毫不差
    拿回来的长度必须 == position - have。少一个字节就报错 —— 这是 CDN 陈旧缓存唯一的防线：拿到旧副本 = 长度不够 = 该群失败，绝不会拿残缺数据去出指标。
  • 02
    必须是完整的 NDJSON 行
    首字节是 {、末字节是 \n。不成立说明上游的 position 压根不在行边界上—— 那比少几个字节严重得多，不能让它变成下游某次 JSON 解析失败。
  • 03
    冷启动时数一遍行数
    整个文件的 \n 个数必须 == ndjson_record_count， 对不上就删掉重来（留着的话下次的 have 就是错的）。
    增量时不数 —— 数一遍要读回整个月文件，月末 1000 群 = 白读 18 GB。

过了三关才 append + sync_all()。追加是原子的顺序写，本地永远是「合法的前缀」。

06

JoinSet · pull_concurrency = 8并发怎么压，失败怎么隔离

月文件一个一个 spawn 进 tokio::task::JoinSet，在飞的超过 pull_concurrency（配置里是 8） 就先 join 掉一个 —— JoinSet 本身就是背压，不用再加信号量。

两种失败在类型上就分开了：PullError::Round 往上抛、整轮死； PullError::Room 进失败集合、该群本轮一行不写。

07

why not ossutil sync为什么不直接 ossutil sync

因为 sync 看见文件变了就整个重下。月文件意味着月末重下的是整月。

省带宽只是顺带。真正的收益是：「文件尾部半行 JSON」这一整类失败被从结构上消灭了 —— 不是检测它，是根本读不到它。

08

measured · 2026-09-01 · dev 索引表 10 行实测跑出来的样子

冷启动10 个月文件落地 107295 字节 / 100 行，与 ndjson_position、ndjson_record_count 逐位相同
幂等再拉一次：新增 0 · 已最新 10 · 零字节下载
增量人为截到 18843 字节（第 20 行末）→ 只补 6213 字节 → 回到 25056，与全量下载 sha256 逐字节相同
超长人为多追加 52 字节 → WARN「本地比上游长，作废重拉」→ 重下 3200 字节，与原文件逐字节相同
行边界人为截到 20000 字节（行中间）→ 该群失败，一个字节都没写
最后一条暴露了一个已认领的代价

have 落在行中间时 have < position，不触发「作废重拉」那一条 —— 这个群会每天失败、永远卡住，要人工删文件才恢复。不修：have 只由 pull 自己写， 而它只写通过校验的完整行块。行中间的 have 意味着磁盘损坏或有人手工改过，那在信任边界之外。

09

unsolved · external还没解决的那个外部问题

filet.jdd51.com 是 CDN，实测响应头：

x-oss-object-type: Appendable              ✅ 确认追加写
x-oss-next-append-position: 21103          ✅ 与索引表 position 逐位相同
accept-ranges: bytes  ·  Range → 206       ✅ 增量可用
x-swift-cachetime: 2592000                ⚠️ 30 天缓存
一个每天都在追加的文件，配了 30 天缓存

Cache-Control: no-cache 请求头不起作用，加随机 query 参数也不起作用 —— 客户端绕不掉。理论上会连续多天拿到旧副本。
兜底就是第 05 步那道字节数校验：拿到旧副本 = 该群失败、记 run_failure， 数据不会写坏，但这个群可能连续失败很多天。
不写自动重试退避 —— 30 天的缓存不是重试几次能解决的，写了只会掩盖问题。

10

ingest.rs · DuckDB拉完之后，怎么读

拉取只负责搬字节，不认识任何业务字段。读是另一件事：DuckDB 直接盖在本地 NDJSON 上， 过滤 / 投影 / 排序全下推给 SQL，不把整表拉进内存。

FROM read_json_auto(['./data/raw/202608/<corp>/<room>.ndjson'],
                    format='newline_delimited', filename=true)
WHERE CAST("at" AS DATE) BETWEEN '2026-08-30' AND '2026-08-31'
ORDER BY "at", msg_id

路径只用来收窄 I/O，正确性靠那个 BETWEEN —— 一个月文件里装着整月， 窗口过滤按消息真实时间做。读一个群 18 MB 大约 70 毫秒，而一次跑批光调模型就是几十分钟。
