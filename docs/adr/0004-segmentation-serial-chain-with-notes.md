# ADR-0004：群内一条串行链传便签，并行只加在群之间

- 状态：**已采纳**
- 相关：`src` ③ 抽取（`_cut` / `_view` / 便签）
- 承重规则的浓缩版在 `CLAUDE.md` 硬规则一节；这里是完整论证与实测数字。

## 决策

1. **段之间串行** —— 后一段要看前一段的便签，群内一个接缝都没有。并行只加在群与群之间。
2. **段内能不切就不切** —— 整段先试一次，只有模型吃不下（`incomplete` / `APITimeoutError`）才对半切。
   **没有阈值参数**，是运行时看信号决定的。
3. **跨段的事件靠便签接住**，不靠规则预防，也不靠按订单号事后合并。
4. **切点在目标位置 ±5% 内挪到时间间隔最大处**，窗口从段长推出，不新增参数。

## ⚠️ 已经删掉的东西，别再加回来

窗口条数上限 · 重叠量 · 静默阈值 · 线程装箱 · 块间并行 —— 全部不存在了。
切分改成运行时自适应二分之后，**没有参数可调**。

## 实测论证

### 群内一条串行链传便签；并行加在群之间

```
一个群一天  ──切成 ceil(n / SEGMENT_MSGS) 段──> 段1 →📝→ 段2 →📝→ 段K
                                                （全群共用一套 drafts，零接缝）
```

- **段之间必须串行** —— 后一段要看前一段的便签。便签贯穿整个群，所以**群内一个接缝都没有**。
- `SEGMENT_MSGS` **不是质量旋钮，是省钱旋钮**：切几段都不产生接缝，它只是省掉第一次拿整群去试、注定被截断的那一次调用。设成「一次调用舒服跑完」的量级。无默认值，缺失即报错。
- **并行加在群与群之间**（跑批天然有几十上百个群），不加在段之间。段间并行等于每个边界丢一个接缝 —— 实测（167 条 / 43 个真实事件）切一刀就切开 **5 个**事件。那是拿准确率换单群延迟，只有「一次只跑一个群」才划算，跑批不是这个场景。
- `ROOM_CONCURRENCY` = 同时跑几个群，是**唯一**能压的墙钟旋钮（段间串行动不得，单次调用的 reasoning 已经关掉了）。无默认值，缺失即报错。
  **约束是 TPM，不是并发数** —— 百炼按 RPM / TPM / 增速三个维度限流，没有「并发连接数」这一说。单次调用 input ~25k token、耗时 ~110s，所以

  ```
  峰值 TPM ≈ N × 25000 × 60/110 ≈ 14000 × N      →      N ≈ TPM额度 / 14000
  ```

  `qwen3.8-flash` 是稳定版（不带日期后缀）。同系列稳定版实测量级 RPM 30000 / TPM 5–10M，**RPM 根本碰不到**（N=32 才 ~17 RPM）。按 TPM 5M 算上限约 360，取 **32** 是留了 10× 余量 —— 余量给的是「TPM 额度要去控制台确认」和**增速限制**（`Request rate increased too quickly`：一次性起 N 个并发任务，即使没到 RPM/TPM 也可能被拦）。
  真到了 429，先看是哪一种（RPM / TPM / 增速），别无脑调小。

  > ⚠️ 现有样本只有 1 个群，**这个数眼下量不出任何东西**。等真实多群数据到了按实际 429 回调。

### 段内：能不切就不切；切了就传便签

**整段先试一次。只有模型吃不下才对半切**，两半按时间顺序跑，切不动了（剩一条仍失败）就抛出 → 该群本日失败。「是否切分」是运行时看信号决定的，**没有阈值参数**。

「吃不下」有两种表现，都要翻译成同一个信号：`status=incomplete`（输出被截断）和 `APITimeoutError`（一次调用没跑完）。**不认 `APIConnectionError`** —— 网络断了切成两半也一样断，把它当「太大」会让一次故障放大成一整棵调用树。

真瓶颈是**输出预算不是上下文**：771 条实测 input 25k（1M 上下文绰绰有余），output 打满、reasoning 占 99.2%。按条数或字符数定上限是量错了地方。

段与段之间传一张**便签** —— 还没闭合的事件，每条一行：`E1: <订单号> · 摘要 ← 上次说到「原话」`。

**便签上必须带订单号。** `summary` 按契约不含 ID，可订单号正是这个群唯一可靠的关联键（下表：误合并率 0.1%）。不带的话模型看到「E7: 商家要求加急，已催促」，根本无从判断本段那条同单号的消息是不是接着它 —— 便签有几十条时这是致命的。订单号由代码从来源消息里**确定性提取**（`_ORDER_NO = [A-Za-z]{0,6}\d{16,}`，`search` 不 `match`），不问模型；但提取出来只是**摆给模型看**，关联仍由模型做，代码不替它 join。

⚠️ **不能锚行首。** 商家习惯把单号写在开头（322 条），可**平台的结构化工单推送一律写在正文中间**（`工单原因：… / 订单号:JDLY… / 三方订单编号:…`、`三方：<单号>`）。锚了 `^` 那 36 条一条都进不了便签 —— 平台侧的关联线索**整个丢光**。改成 `search` 后可标注的消息 322 → 358。

单号形态实测（1096 条）：19 位纯数字 230 条 · 22 位字母数字 78 条 · 16 位 10 条。**16 位下限是为了挡掉手机号**（11 位，3 条）—— 手机号是「联系客户用」的，一个客服名下十几单共用一个，当关联键会把不相干的单焊死。

⚠️ **订单号是「工单」的钥匙，不是「事件」的钥匙。** 同一个单号下可以有好几件互不相干的事：实测同单号且**间隔 0 行**的两个事件，一个是「加同款保护拆」一个是「加灯具维修」。所以它只进便签给模型当线索，**不能拿来在代码里合并事件** —— 那把钥匙是 `replyTo`。

**便签只加不减，所以要按历史条数淘汰。** 根因是 `still_open` 只在模型这一段又提到该事件时才更新，没提到就永远开着 —— 而派单群里「客服说安排了、然后没下文」是常态，不是异常。1096 条实测便签已堆到 **75 条**（早先「≤10 行、占窗口 5–7%」是每块独立 drafts 时代量的，已作废）。

⚠️ **便签不是性能问题，别拿它当性能杠杆。** 实测把第 3 段的便签从 75 条压到 17 条，墙钟 5:08 → 5:37（噪声内），事件数 280 → 280、跨边界事件 4 → 4 一个不差。串行 5–6 分钟就是 3 次调用 × 约 110s，`.env` 里「400 条 36s」那个数已经过时。便签淘汰的价值是**封住无限增长**和**不稀释注意力**，不是提速；提速要靠群级并行。

- **上一整段都没动静的事，撤下便签。** 判据是 `lo - 最后一条消息下标 > SEGMENT_MSGS` —— **复用段长，不另发明一个数**。依据是群聊现实：隔太久的事已经被刷没了，现实中没人会再接着说。
- **例外：本段有人显式 `replyTo` 它就捞回来，多远都捞。** 实测最远回指 **947 条**；`replyTo` 覆盖 24%、回指距离 P50 仅 4 条 / P90 45 条，所以这条例外很少触发但不能省。
- **撤下便签 ≠ 丢掉事件** —— draft 还在 `drafts` 里照样输出，撤的只是「拿给模型看的那一份」。这是注意力问题，不是存储问题。
- 日志 `[便签] lo:hi 带 N/M 条`：N = 带进去的，M = 还开着的，差额就是撤下的。
- 段长是**模型输出预算**的性质，便签深度是**人的注意力**的性质，眼下量级相同才合用一个数。换了输出预算大得多的模型、段长跳到几千时，把便签窗口拆成独立常量（代码里有 `ponytail:` 标记）。

实测（`SEGMENT_MSGS=365` 跑）第 3 段便签 75 → 17 条，**事件数 280 → 280、跨边界事件 4 → 4 一个不差**，撤掉的 37 条确实是死的。回指超过 365 条的全样本只有 3 条且都被 `replyTo` 捞回。

- **不重叠、不去重。** 每条消息恰好属于一段。重叠会让同一条消息进两段、被引用两次，去重就跟着回来了。
- **跨段的事件靠便签接住**，不靠规则预防（规则对 60% 的灰消息说不出话），也不靠按订单号事后合并（钥匙只有 27% 的碎片两边都有，且同一单号下常有好几件互不相干的事）。便签是有效的：`SEGMENT_MSGS=400` 实测**跨段事件只有 7 个**。
- **断开在段内，不在段边界。** 所以对齐（`_align`）是抽取完整体跑一次，不逐段跑 —— 便签已经把跨段那 7 个接住了。钥匙是 `replyTo` 不是订单号，见 **ADR-0002**。
- **切点在目标位置 ±5% 内挪到相邻消息时间间隔最大的那一处**（`_cut`）。纯下标算出来的切点对会话结构完全盲目：真时间戳实测 `[0,365)` 二分的中点 182 处间隔仅 **187 秒**，而全样本最大的间隔（**24323 秒**的隔夜断点）就在 9 条之外；顶层切点 365 处间隔只有 **2 秒**（切在一串连发消息中间），挪到 378 是 471 秒。窗口从段长推出，**不新增参数**，再被 `(上一个切点, 下一个切点的目标位置)` 夹一次 —— 夹这一下是承重的，没有它挪动会一路把切点推向末尾、后面没位置放剩下的切点（`cap=1` 时每条一段，一点余量都没有）；夹完窗口至少还含目标位置本身，所以恒非空、恒严格递增，划分性质不受影响，没余量时自动退化成不挪。
  收益是边际的（便签本来就接得住跨段事件），但成本接近零。曾评估过最小成本 DP 分段（切断线程 26 → 15），那个仍然不做 —— 便签已经把这些都接住了。
- 这些全部是 ③ 抽取模块的**内部**行为，不上浮到接口上。

**群内已经没有接缝了。**万一将来又冒出接缝（比如有人把并行加回段之间），**只有订单号这一把钥匙能用**。在 43 个真实事件上实测的误合并率：

| 关联键 | 接回被切开的事件 | 误合并（不该合却合了） |
|---|---|---|
| **订单号** | 4/5 | **0.1%**（1/903 对） |
| 人员 | 3/5 | ❌ **33%**（298/903） |
| 时间 ±30min | — | ❌ **26%**（234/903） |

派单群是几十单并行跑的：一个客服名下 10 个不同单号，±30min 内 9 单同时活跃。**人员和时间会把不相干的事件焊死，不能进关联键。**
