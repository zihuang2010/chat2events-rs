承重不变量 1 · 冻结

冷冻区是怎么更新的

事实列
永远不更新。没有入口，也没有人回去改。
标注列
只在换词表那一天，整体重贴一次标签 —— 不重跑模型。
冻住 · 本轮不可写 本轮可写 · 每轮删重写 守卫拦截

01 / 线在走不是有人去改老数据，是冻结线每天往右挪一格

跑批只看窗口里的那几天。窗口每天整体右移，昨天还能写的那一格，今天就落到线的左边 —— 它没被改动，只是不再被任何一条 SQL 指向了。

02 / 一行分两半一条 event 上，只有两列是可以事后改的

十二列事实由那一次抽取定死；两列标注是贴上去的标签。冻结管的是前者。

03 / 两道锁跑批就算想写冷冻区，也写不进去

第一道是构造：删重写的 IN 列表里只有窗口那几天。第二道是守卫：真有事件算到了窗口外， 写库之前就拦下，那个群整轮失败、一行不写。

04 / 唯一的入口换词表那天，把标签整体重贴一遍

拿早就存好的 summary 重新查一次分类，写回两列，再重算指标。 一次抽取模型都不调，一个 token 都不烧。

05 / 为什么不许重抽事实制造的是抖动，不是修正

同一份聊天记录，模型不保证抽出同样多的事件

所以冻结区不是"暂时懒得重算"，是拒绝重算：报表要能拿去做同比环比，历史数字就必须钉死。

06 / 四条脚注诚实地说，还有这些

  1. 指标表不受冻结约束。它依赖的事实全都还在，随时可以整体重算 —— 换归属口径（first_responder ↔ all_participants）同理，不用重跑 LLM。
  2. 冻结线的位置由配置决定。lookback_days 今天是 5， 所以窗口是 [T-5, T-1]（CLAUDE.md 里写的 T-2 是它还等于 2 时的说法）。 把它调大，就是在亲手把冻结线往左推 —— 那是有意打破不变量 1，不是正常入口。
  3. 真想重跑更早的天，本地也没料了。raw 区滚动只留 2 个月，更老的月目录每轮跑完就删。 要重跑得整月重下（ADR-0005）。
  4. 今天冷冻区其实一次都没被更新过。词表还在 v0，全部 __untyped__； 而那条 recompute --taxonomy-version vN 的 CLI，Rust 版还没搬（docs/status.md ⑥ 行）。 上面第 04 节讲的是设计好的唯一入口，不是今天已经能跑的命令。
